# Производительность туннеля на носителе VK Calls

<!-- // ai-generated: the whole file (carrier measurement notes, nl-yar pair). -->

Замер пары сервер-клиент на реальном носителе: сервер в Амстердаме (yar),
клиент в Амстердаме (nl), обе ноги к SFU VK 37-52 ms, комната одна. Прогон:
`audit/bench-tunnel.sh` на клиенте, curl через SOCKS5 клиента до
speed.cloudflare.com; выход трафика с сервера. Профили: `pprof.listen` в
конфиге, `/debug/pprof` на loopback обеих сторон.

## Числа

| Метрика | Значение |
|---|---|
| Прямой канал каждой стороны | 45-64 MB/s |
| Туннель, длительная отдача | 14-21 Mbit/s (медиана прогонов ~18) |
| Туннель, всплески 8 MiB | 13-17 Mbit/s |
| Туннель, приём (upload) | ~16 Mbit/s |
| TTFB 16 KiB | 260-300 ms |
| CPU под нагрузкой | сервер ~24%, клиент ~32% |
| Оверхед туннельного слоя | ~0.15% |

TTFB раскладывается на ноги SFU (2 x ~50 ms), очередь релея и RTT сервера до
Cloudflare; сам протокол добавляет десятки миллисекунд.

## Выводы

- Узкое место - SFU VK: поток полисится на ~2.2-2.5 MB/s в секунду
  длительно, кратко пропускает до ~3.2 MB/s, лишнее отбрасывает.
- Доля потерь масштабируется со скоростью отдачи: ~3% на равновесии, ~22%
  при удвоении темпа. Контроллер olt (BBR) при агрессивной пробе (1.6)
  получает рост потерь и падение полезной скорости; при сглаженной (1.1) -
  заниженную оценку полосы и те же ~1.1 MB/s. Штатные константы (1.25/0.75,
  цикл 8 фаз) - оптимум из трёх проверенных точек.
- Контроллер держит равновесие честно: btlbw совпадает с доставкой,
  retx примерно равен потерям, spurious ~1%.
- SRTP-профиль выбирает SFU как DTLS-сервер: согласуется AES_CM_SHA1_80,
  AEAD-GCM со стороны клиента не навязать. HMAC-SHA1 в CPU-профиле - цена
  этого выбора, ~13% ядра на клиенте.
- Подъём `vp8.fps` на обеих сторонах до 240 дал 2.3 -> 2.9 MB/s (граница
  пейсинга 60 fps x 60 KiB); только на сервере эффекта нет: темп ACK
  задаёт клиентский тикер.

## Что это значит для оптимизации

Код протокола на этом носителе - не узкое место: туннельный слой доставляет
без потерь и оверхеда, контроллер работает на пределе, который разрешает
SFU. Существенный рост сквозной скорости требует пути мимо SFU (прямой UDP,
ретранслятор) либо подъёма полисинга самим VK. На текущем носителе
сервер-онли изменений кода, дающих сквозной прирост, не найдено; ниже -
что проверено и отклонено.

- Проба BBR 1.6 и minRTTWin 20 s: скорость ниже базовой, TTFB выше. Отклонено.
- Проба BBR 1.1/0.9: равновесие 1.1 MB/s. Отклонено.
- AEAD-GCM вместо SHA1_80: выбор за SFU, навязать нельзя. Отклонено.
- `vp8.fps` только на сервере: без эффекта (ACK тикает клиент). Отклонено.

Оставлено: `pprof.listen` - listener `/debug/pprof` процесса (по образцу
`stats.listen`, пустое значение выключает). Профили CPU на живой паре
показали расклад: syscalls 19-30%, SRTP (AES-CTR + HMAC-SHA1) ~13%,
memmove/malloc - остаток; обработка кадров и KCP в топ не входят.
